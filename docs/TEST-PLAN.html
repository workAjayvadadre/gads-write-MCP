01   Where the suite stands

422 tests, no network, no credentials. Genuinely well pinned, and worth not re-testing:

PropertyHow it is pinned
Micros conversionLiteral expected values, not recomputed the way the code does — so the tests can actually disagree with the implementation
Fail-closed behaviourUnregistered tool, unknown enum, lookup outage, missing email, unreadable MCC — each has a test
Plan lifecycleOwnership, expiry (including the exact boundary), single-use, replay, unguessable IDs
Kill switchHides tools, refuses calls, checked before the tier lookup, does not block reads
AuditExactly one line per decision, refusals logged too, arguments redacted, account timezone used
Human approvalRequired, and a client that cannot elicit is refused rather than waved through
Query fieldsEvery SELECT clause parsed and checked against the pinned v25 protos
Hostile percentagesinf, Infinity, nan, 1e999 all refused at boot
What a green suite does not mean

Twice in the last week this suite was green while a real defect was live: a plan could be applied under limits it was never checked against, and a config typo could take the server down while /healthz reported healthy. Both were found by reading, not by testing. Everything below is chosen because no existing test would catch it.

02   Concurrency — the big hole

There is not one asyncio.gather, thread, or concurrent task anywhere in tests/. Every shared, mutable thing in this server is therefore tested only single-file.

C-1

Two confirms race the same plan

High
Setup
One drafted plan. Two confirm_and_apply calls on the same plan_id, launched together with asyncio.gather, both approving at the elicitation prompt.
Expect
Exactly one succeeds. The other fails with already used. executor.applied has length 1 — never 2.
Why
This is the single most expensive possible bug: the same budget change applied twice. The consume step is a compare-and-swap under a lock and should hold, but nothing proves it.
C-2

Two plans confirmed across the approval wait

High
Setup
Two separate budget plans by the same person. Call confirm on both, and hold both elicitation prompts open before approving either.
Expect
Decide what you want here first — see the note below. At minimum, the audit log must record both real increases, and the preview each person approved must reflect what was actually applied.
Why
The gate reads state, then waits an unbounded time for a human, then applies. Anything read before that wait is stale by the time it matters.
C-3

Interleaved audit writes stay parseable

Medium
Setup
Fire 50 concurrent gate checks. Then read the log back through AuditLog.iter_records.
Expect
50 well-formed lines, none truncated or interleaved mid-line.
Why
The daily spend total is derived from this file. A torn line is silently skipped, and skipping means handing back allowance.
C-4

Caches under simultaneous first use

Medium
Setup
Cold TierCache and ManagedAccountStore. Ten concurrent callers, with the underlying lookup counting how many times it is actually invoked.
Expect
A consistent answer for all ten, and no cached failure if the lookup raises.
Why
A stampede is a performance problem; a cached failure is a correctness one. Only the second really matters, and only a concurrent test shows it.
A decision to make before writing C-2

The per-user daily total is no longer a refusal — it is shown on the preview so the person approving can judge. That is a deliberate choice, and it means "two confirms exceed the cap" is no longer a bug by definition. What is still worth pinning is that the number shown and the number recorded are both true. Write the test against that, not against a cap that no longer exists.

03   Time and timezone

Now sharper than before: the timezone is no longer configured, it is read from each account. Two accounts in one request path can legitimately be on different days.

T-1

Spend rolls over at the account's midnight, not UTC's

High
Setup
Account on Asia/Kolkata. Drive the clock to 18:45 UTC — which is 00:15 the next day locally. Apply a budget increase before and after.
Expect
The two land in different dated audit files, and today's running total resets at local midnight.
Why
UTC and IST differ by 5:30, so for over five hours a day the "today" total is wrong if the wrong clock is used.
T-2

Two accounts, two timezones, one person

Medium
Setup
One caller changing budgets on an Asia/Kolkata account and a America/New_York account within the same hour.
Expect
Each change is dated by its own account's timezone. Define and assert what "today's total" means for a person spanning both.
Why
This became possible the moment the timezone stopped being one server-wide setting.
T-3

A plan drafted before midnight, confirmed after

Medium
Setup
Draft at 23:58 local, advance past midnight, confirm at 00:03.
Expect
No crash; the audit line lands on the day it was applied.
T-4

Retention pruning never deletes a day still in use

Low
Setup
Retention of 1 day, with files for today, yesterday and last week.
Expect
Today survives. Always. Prune uses a UTC date while files are named by local date, so check the boundary explicitly.

04   Money edge values

The rule set shrank deliberately — one relative backstop instead of absolute bands. Fewer rules means each remaining one carries more weight.

M-1

The backstop at its exact boundary

High
Setup
With the backstop at 100%: raise 100 → 200 (exactly 100%), then 100 → 200.01.
Expect
The first is allowed, the second refused. Inclusive, and stated as such.
Why
<= versus < is invisible on inspection and is the likeliest bug in any limit.
M-2

Zero, negative, and rises from zero

High
Setup
Budgets of 0, -1, 0.0001; and a rise from a current budget of exactly 0.
Expect
Zero and negative refused. A rise from zero refused with the "percentage is undefined" message, not a division error.
M-3

Sub-currency-unit amounts

Medium
Setup
new_daily_budget = 100.005, which is 100,005,000 micros.
Expect
Decide the behaviour, then pin it. Google rejects amounts that are not a multiple of the currency's minimum unit — and it does so after the plan is consumed and a human has approved. Refusing at draft is friendlier.
M-4

Very large and precision-losing values

Medium
Setup
A budget at the sanity ceiling, one just over, and a float like 0.1 + 0.2 arriving through the tool interface.
Expect
Refused cleanly with a readable message; never a silent overflow or a binary-float artefact reaching micros.

05   Preview vs what applies

The preview is the entire approval model. If it can ever describe something other than what applies, every other control is decoration.

P-1

The approved preview matches the mutation, field by field

High
Setup
For each write tool: draft, capture the preview text, confirm, capture the MutationRequest.
Expect
Every number in the preview appears in the payload, converted correctly. Assert on parsed values, not substrings.
Why
Preview and payload are derived separately from the same variables. Nothing structurally prevents drift.
P-2

Every entity mutated is named in the preview

High
Setup
A budget shared by three campaigns; a campaign moved to another budget between draft and confirm.
Expect
Refused, both at draft and at confirm. Regression tests exist for both — keep them, and add the shared case at draft.
P-3

A warning on the preview is actually present

Medium
Setup
Broad match on a manual-CPC ad group, now a warning rather than a refusal.
Expect
The plan is created and the preview carries the warning. A rule downgraded to a warning is only safe if the warning reliably appears.

06   Failure modes

Ask, at every point where the server talks to Google or the disk: what if this fails here?

F-1

Google fails at each step of confirm

High
Setup
Inject a failure at: the re-read, the account-total fetch, and the mutate itself.
Expect
The first two refuse without consuming the plan. The third consumes it and says plainly that the outcome is unknown and a human must check the account.
Why
The distinction between "refused" and "used up" is the difference between retrying safely and double-spending.
F-2

The audit log cannot be written

High
Setup
Make the log path unwritable, then attempt a change.
Expect
The mutation does not happen. An unloggable change must be refused, not applied silently.
F-3

A corrupt or truncated audit line

Medium
Setup
Append half a JSON line, then read the day's total.
Expect
The bad line is skipped and surfaced somewhere. Skipping silently hands back allowance, which is the fail-open direction.
F-4

A missing audit file is not the same as no spend

Medium
Setup
Delete today's dated file, then read the total.
Expect
Currently this reads as zero used. Decide whether that is acceptable and pin the answer either way.
F-5

A bad roles.yaml keeps the last good table

Medium
Setup
Invalid YAML, then valid-YAML-wrong-shape, then a deleted file.
Expect
Last good table retained, last_error set, /healthz 503. The deleted-file case currently reports healthy — worth deciding on.

07   Accounts and permissions

The account set now comes from the MCC rather than a list, which is newer code and carries the most recent risk.

A-1

An account outside the MCC is refused, everywhere

High
Setup
A customer ID the caller genuinely has access to on their own Google login, but which is not under the manager account. Try every read tool and every write tool.
Expect
Refused for all of them. This protects the developer token, so a gap here is an attribution problem, not just a permissions one.
A-2

"Not ours" and "could not find out" stay distinct

High
Setup
An unknown account with a healthy MCC lookup, versus a failing MCC lookup.
Expect
Both refuse, with different audit verdicts. An outage must read as lookup_failed, not as a wave of correct refusals — otherwise nobody can tell an outage from ordinary use.
A-3

Each account is judged in its own currency

Medium
Setup
Two managed accounts, one INR and one USD.
Expect
Previews and messages use each account's own currency code. Nothing compares a figure in one currency against a limit expressed in another.
A-4

Demotion from lead to operator, mid-plan

Medium
Setup
Lead drafts a lead-tier change; demote to operator; confirm.
Expect
Refused. Note that demoting to readonly does not test this — the middleware catches that earlier, which is exactly how this went untested for months.
A-5

health_check tells a stranger nothing useful

Medium
Setup
A caller at tier none calls health_check. Separately, hit /healthz while a config reload is refused.
Expect
No customer IDs, no email addresses, no file paths in either response. Both currently leak in at least one path.

08   Tests that need repairing

These exist and pass, but do not prove what their names claim. A misleading test is worse than a missing one, because it stops anyone looking.

TestProblem
test_the_daily_ceiling_accumulates_across_changesAsserts deltas == [10,15,20], recomputed as target − 100 — the same subtraction the code performs, so it can never disagree. Assert against independently-known values.
Update-mask testsAssert paths <= ALLOWLIST, which the code already raises on — the assertion cannot fail. Add a case that drives the seal into actually refusing.
Refusal-message assertionsassert "20" in message passes on "120". Match the rule that fired, not a digit that happens to appear.
Fakes vs the summary objectsFakeReader is hand-maintained. When a real summary gains a field, the fake silently returns the default. Build fakes from the real dataclass so a new field is a visible decision.

09   Live-account tests

No request has ever left this process

Every test uses a fake executor or an offline client. Proto construction, enum lookups and update-mask logic are exercised for real, but nothing has ever been sent to Google. These are the cases only a live account can settle — run them on a test account first, in this order.

L-1

A non-admin can read their own access role

Do first
Do
Have a real STANDARD or READ_ONLY user connect and call health_check.
Expect
Their tier resolves. If it fails, the whole "add them in Google Ads and they just work" model needs the documented fallback — and you learn it now rather than on rollout day.
L-2

Reads return real shapes

Live
Do
list_accounts, then get_campaign_performance and get_search_terms on a real account.
Expect
Sensible numbers. Cross-check spend and clicks against the Google Ads UI for the same window — this is where a micros error or a timezone shift shows itself.
L-3

The first mutation is a pause

Live
Do
With GADS_WRITE_ENABLED=true, pause one campaign that does not matter. Approve the prompt. Then enable it again.
Expect
The change appears in the Google Ads UI. The audit log has a line for each. Crucially: the campaign's name is unchanged — a mask naming an unset field is how a status change silently blanks a name.
L-4

A budget change, then read it back

Live
Do
Raise a test campaign's daily budget by a small amount, approve, then re-read it.
Expect
The new amount matches the preview exactly. A 1,000,000× error is unmistakable here and nearly invisible anywhere else.
L-5

The refusals actually refuse, against real data

Live
Do
Attempt a change on a genuinely shared budget; attempt one on an account outside the MCC; attempt a raise past the backstop.
Expect
All refused, with the message you expect. Verified against fakes, never against Google.
L-6

The approval prompt works in the real client

Live
Do
Run a write end to end through Claude's own connector UI.
Expect
A prompt appears and declining it changes nothing. Elicitation has never been exercised against that client — if it is unsupported, writes refuse rather than misbehave, but you want to know before rollout.

10   The habit that matters most

More valuable than any single case below: before trusting a safety test, break the thing it guards and watch it fail.

# 1. comment out the check
# 2. run only that test  →  it MUST fail
# 3. restore, confirm green

This caught two problems in this codebase in one afternoon. A test asserting the confirm-time tier check passed against a deliberately broken build, because a different check refused first — it was pinning the wrong line entirely. Another guard turned out to be pinned by three tests that all failed for the same unrelated reason.

Back up the file first

Restore with a per-file copy, not git checkout -- <directory>. That command reverts every uncommitted change in the directory, which is a fast way to lose an afternoon of work that was never committed.

Suggested order: C-1 and F-1 first — both are cheap and both guard against double-spending. Then the P group, because the preview is what every other control rests on. The L group only after everything else is green, and only on a test account.

Written against bc11c0c. The rules changed materially in the three commits before it — absolute limits removed, the daily total downgraded from a refusal to information, accounts derived from the MCC — so re-read the module docstrings before writing against any rule named here.
