Is gads-write-mcp safe to ship?

A production-readiness review of the guardrailed Google Ads write server — the one that can spend real money. Five review passes over the whole codebase: the write path, authorization, Google Ads API usage, the safety core, and the tests.

commit 3d7ca4b 375 tests passing ~4,900 lines under review 2 Sep 2026

Not yet. Seven things must be fixed first.

The architecture is sound and the guardrails are real — this is a well-built system. But one defect can take the whole server down silently, the most important permission check has no test behind it, and three separate bugs let a budget change slip past the limits it was approved under. None are hard to fix.

The pattern behind half the bugs

Every write happens in two steps. You draft a change and get a preview plus a plan ID; nothing happens yet. Then you confirm, and only then does the mutation reach Google. The whole safety model rests on the confirm step re-checking everything, because time has passed and the world may have moved.

A fix earlier this week made confirm re-run the policy rules properly. What it didn't fix is subtler: confirm re-derives the checks, but not the things being checked against. The amount is re-read. The budget it points at, the spend figure written to the ledger, and the running total the ceiling is measured against are all still whatever they were at draft time.

Must fix before release

In the order I'd tackle them. Numbers are a fix sequence, not a ranking of blame.

01

A small config typo can take the server down — while the health check says everything is fine

Critical Confirmed bug I reproduced this

The policy file is designed to be edited live. If someone writes invalid YAML, the server correctly keeps the last good version and carries on. But if the YAML is valid and merely mis-shaped — a tier's budget: block left empty — the loader raises a different kind of error than the one the safety net catches. It escapes into the live request.

What that looks like

A lead deletes four lines under limits.tiers.operator.budget and saves. From that moment every single tool call returns a 500 error, forever, and it never recovers on its own. Meanwhile /healthz — the endpoint built specifically to make silent config problems visible — returns 200 ok, because the error was never recorded. Both documented guarantees fail at the same moment.

call 1: TypeError ESCAPED -> argument of type 'NoneType' is not a container or iterable
call 2: TypeError ESCAPED -> ...
last_error: None          # so /healthz reports "ok"

policy.py:117 · policy.py:353 catches only PolicyError · health.py:57 reads only last_error · settings.py has the same gap, so a bad file also kills startup with a raw traceback

02

The most important permission check has no test behind it

Critical Missing test I verified the gap

Some tools need the higher lead tier — raising bids, adding keywords, creating ads. When someone confirms a plan, the server correctly checks the tier of the tool that drafted it, not the confirm tool. That's what stops a lead drafting an expensive change and an operator applying it.

The code does this right. Nothing tests it.

Why the existing tests miss it

Every demotion test drops the user to readonly — and the middleware rejects a readonly user before the confirm code ever runs. So the tests pass through a completely different door. Nobody tests a demotion from lead to operator, which is the case that matters. You could break this check and the entire 375-test suite would still go green.

confirm.py:214 (correct) · test_write_tools.py:392, :433 and test_middleware.py:220 all demote to readonly

03

The shared-budget guard reads the wrong field from Google

High Confirmed bug Verified against the v25 protos

A shared budget feeds several campaigns at once, so changing it affects all of them — while the preview a human approves names only one. The server refuses these outright, and that refusal is load-bearing for the whole approval model. It checks a field called explicitly_shared.

Google's own definition of that field, read from the installed library: "Specifies whether the budget is explicitly shared. Defaults to true if unspecified in a create operation. If false, the budget was created with the intention of only being used with a single campaign." That is a record of what someone intended when they created it — not what is true now. The field that states the fact is reference_count: "the number of campaigns actively using the budget."

It fails in both directions

A budget created with explicitly_shared=false and later attached to three campaigns sails through the guard — a human approves a preview naming one campaign, and three campaigns' spending changes. Going the other way, a budget created through the API for a single campaign defaults to true and gets refused for no reason.

reads.py:442, :460 · writes.py:362 · fix: select campaign_budget.reference_count and refuse when it's above 1

04

Confirm can check one budget and change a different one

High Confirmed bug

Two halves of one problem, both of which survived the earlier fix. The shared-budget flag is never re-checked at confirm — tick "shared" in the Google Ads interface inside the ten-minute window and the change still applies. And the budget's address is frozen at draft time and used as-is.

What that looks like

You draft a change to campaign X, which uses budget B. Before you confirm, someone repoints campaign X at budget C, which sits at ₹5,000/day. Confirm re-reads and sees ₹5,000, decides that going to ₹120 is a harmless decrease, approves it — and writes ₹120 to budget B. The policy was evaluated against a budget the mutation never touches.

operations.py:203 reads only the amount · writes.py:430 freezes the address · executor.py:277 uses it verbatim

05

The spend ledger records the wrong number

High Confirmed bug

Each person has a daily cap on how much they can raise budgets by, and it's deliberately derived from the audit log rather than a counter in memory — so a restart can't clear it. That's a good design. But confirm writes the increase it calculated at draft time into the log, while the limit check uses a freshly calculated one.

What that looks like

Budget is ₹5,000. You draft a raise to ₹5,500 — the plan records ₹500. Before you confirm, someone lowers the budget to ₹4,700. Confirm re-reads, sees a 17% rise, allows it. The real increase is ₹800, but the log records ₹500. You've permanently recovered ₹300 of your daily allowance, and you can repeat it.

confirm.py:165 reuses the plan's figure · the fresh one is computed in policy.py:459

06

The daily cap can be stepped over by approving two changes at once

High Confirmed bug

The cap is read at the moment the gate runs. Then the server pauses and asks a human to approve the change — a wait with no time limit. The spend total isn't written until after the approval comes back.

What that looks like

Your cap is ₹50/day. Draft two ₹40 raises. Call confirm on both before approving either. Both read the ledger at ₹0 used, both pass, both apply: ₹80 against a ₹50 cap. This needs no special tooling and no concurrency — two ordinary turns in the chat client will do it.

guards.py:267 reads the ledger · confirm.py:237 then waits for a human · nothing serialises the two

07

The shipped configuration is still placeholder

Release gate Already known

The account allowlist in config/policy.yaml is still "0000000000", and config/roles.yaml still ships mode: file — in which the tier resolver ignores the account entirely, so the per-account permission model the project is built around doesn't exist as configured. The single lead entry is lead everywhere.

Both are recorded in CLAUDE.md already. Listing them here because they're release gates, not discoveries.

What's genuinely solid

Worth stating plainly, because it's most of the system and the findings above shouldn't obscure it.

  • Claiming a plan is a proper atomic operation — two people confirming the same plan at once cannot both succeed, and a double-apply is impossible.
  • Everything fails closed. An unregistered tool defaults to the highest tier, an unrecognised permission value maps to none, and a failed permission lookup refuses rather than guessing. Failures are never cached.
  • The none and readonly spending limits are pinned to zero in code, not trusted to the config file.
  • No token or secret is ever logged.
  • Enum lookups, resource paths, ad construction and the “don't let Google bury errors in a 200 response” setting are all correct — verified against the installed v25 library, not from memory.
  • Money conversion tests use literal expected values rather than recomputing them, so they can actually disagree with the code.
  • Human approval sits in exactly the right place: after the policy gate, before the plan is used up. A client that can't ask a human is refused rather than waved through.

Suggested order

01The config crash — it's the only finding that can take the whole server down without anyone noticing.
02The untested permission check — small, and right now nothing would catch a regression in it.
03The wrong Google field — a one-line query change on a guard the approval model depends on.
04–06The three staleness bugs. They're one shape and are best fixed together.
07Real configuration, last, once everything above holds.
