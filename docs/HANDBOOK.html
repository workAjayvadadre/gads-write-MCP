01   What this server is

An MCP server that lets someone change a Google Ads account by asking Claude in plain English — "pause the brand campaign", "raise the budget on X to 500". It is a separate process, on a separate hostname, from the existing read-only Google Ads MCP.

The premise

This server spends real money. Every design decision in it starts from that. Guardrails are not a feature here; they are the product. A read-only server that is wrong shows a bad number. This one, if wrong, moves a budget.

Three ideas carry the whole design:

  • Nothing writes directly. A write tool never changes anything — it returns a preview and a plan ID. A separate call applies it, and re-checks everything first.
  • Every call uses the caller's own Google login. There is no service account or stored refresh token anywhere. Remove someone in Google Ads and they stop working here immediately, with nothing to redeploy.
  • Everything fails closed. An unknown tool, an unrecognised permission level, a lookup that times out — all refuse. There is no path where uncertainty means "allow".

02   The journey of one request

Someone types "pause the Brand – Exact campaign" into Claude. Here is everything that happens, and which file owns each step.

03   Each layer, explained

Nginx — ops/nginx.conf

Terminates TLS and proxies to 127.0.0.1:8081. Two defaults had to be changed, and both matter:

  • proxy_buffering off — the MCP endpoint streams responses as server-sent events. Buffered, they arrive in one lump at the end or not at all.
  • proxy_read_timeout 300s — a tool call waiting on the Google Ads API can outlast the 60-second default and get cut off mid-response.

It also sets X-Forwarded-Proto, without which the OAuth callback is built as http:// and Google rejects it.

FastMCP and OAuth — server.py, auth/identity.py

The whole app is constructed once at import time in server.py — the composition root. Nothing anywhere reaches for a global, which is exactly why the test suite can build the same objects against fakes.

FastMCP's GoogleProvider handles the OAuth dance and validates the token on every request. auth/identity.py then reads the caller's email from the Google-signed token — never from a tool argument or an HTTP header, both of which the caller controls.

Why MCP needs its own authorization layer

There are no URL paths in MCP. Every request is POST /mcp with the tool name as a string in the JSON body — so you cannot write app.use('/admin', requireAdmin). tools/registry.py is the lookup table that replaces route-based auth, and a tool missing from it defaults to the highest tier.

Tier middleware — mcp_middleware.py

Two hooks doing two genuinely different jobs, and confusing them is a real mistake:

  • on_list_tools filters the menu, so a read-only analyst never sees a budget tool and their Claude never proposes one. This is user experience.
  • on_call_tool refuses the call. This is security.

Both are needed: tools/list and tools/call are independent requests, so a client can call a tool it never listed or cached an hour ago before the user was demoted.

The gate — safety/guards.py

The authoritative decision. Every tool calls it before doing anything else, and it always writes exactly one audit line. The order is deliberate:

#CheckRefuses when
0RegisteredThe tool is not in registry.py at all
1Kill switchGADS_WRITE_ENABLED=false and the tool writes
2IdentityNo verified email on the request
3Tier, for this accountCaller's role is below what the tool needs
4Account allowlistCustomer ID is not in policy.yaml
5Blocked operationOperation is on the blocklist
6Field validationArguments are malformed
7–8Policy limits + daily ceilingOver a tier limit, or over today's spend allowance

The ledger read comes last because it is the only check that touches the filesystem — and it only happens when a rule actually needs it.

Talking to Google — ads/reads.py, ads/executor.py

Exactly two modules may talk to the Google Ads API: reads.py for every query, executor.py for every mutation. A test fails the build if a mutate call or a get_service appears anywhere else. One execution path means the audit log cannot be bypassed and there is one place to look when asking what could possibly have changed an account.

ads/client.py builds a client per request from the caller's own token. There is no refresh token on disk anywhere in the repo.

The audit log — safety/audit.py

Append-only JSON lines, one file per day (logs/audit-2026-09-03.jsonl), pruned in-process after GADS_AUDIT_RETENTION_DAYS.

Do not add a logrotate rule

The per-user daily spend ceiling is rebuilt from these files rather than held in a counter — so a restart cannot clear someone's allowance. The flip side: an external tool that truncates or moves them silently gives everyone a fresh allowance, with no error and no log line. Rotation is in-process precisely so that no routine ops action can disable a security control.

04   The two-step write

This is the heart of the system. A write tool does not write.

A plan carries intent, never authority. Between drafting and confirming, someone may have been demoted, the account may have left the allowlist, or a lead may have tightened policy.yaml. Re-checking is what makes that true rather than merely stated.

Two ordering decisions are worth knowing:

  • Approval comes after the gate, before the plan is used up. Nobody is asked to approve something policy would refuse anyway, and declining leaves the plan open rather than burning it.
  • The plan is consumed before the mutation, not after. If the apply crashes halfway, the plan is already spent — so nobody blindly retries when we cannot know whether the change reached Google. A human has to look at the account. The alternative turns a timeout into a double-apply.
Human approval is enforced by the server

confirm_and_apply uses MCP elicitation to show the preview to a person and applies nothing unless they accept. A client that cannot show an approval prompt is refused, not waved through — failing open would leave exactly the hole this closes. Controlled by GADS_REQUIRE_HUMAN_CONFIRMATION, default true.

05   Every file, and its job

Entry and configuration

server.pyComposition root. Builds everything once, wires it explicitly, registers the tools, starts FastMCP.
settings.pyReads and validates the environment. Collects every problem and reports them together, then refuses to start.
health.pyUnauthenticated /healthz. Returns 503 when a config reload was refused.
mcp_middleware.pyFilters the tool menu; refuses calls above the caller's tier.

Who is calling — auth/

identity.pyReads the caller's email and Google access token from the validated OAuth token.
tiers.pyThe four levels: none → readonly → operator → lead.
roles.pyFile-backed resolver, reading roles.yaml. Hot-reloads; keeps the last good version on a bad edit.
google_ads_roles.pyResolves a tier from Google Ads itself, per account, with a short cache. Add someone in the Ads UI and they work here.

The safety core — safety/

guards.pyThe gate. Runs every check in order and always writes an audit line.
policy.pyLoads and hot-reloads policy.yaml; holds the pure rule functions.
plans.pyDraft plans: owner-bound, time-limited, single-use, in process memory.
spend.pyPer-user daily ceiling, derived from the audit log rather than a counter.
audit.pyAppend-only log, partitioned by date, prunes itself.
units.pyMoney. Micros conversion, always Decimal, never float.
validators.pyInput validation, and the backstop against query injection.

The tools — tools/

registry.pyWhich tier each tool needs, and whether it writes. Route-based auth's replacement.
reads.pyRead tools: accounts, campaign performance, search terms.
writes.pyDraft tools. Return a preview and a plan ID; change nothing.
operations.pyThe checks for each write tool, in one place, used by both steps.
confirm.pyThe only thing that applies a plan.

Google Ads — ads/

client.pyBuilds a per-request client from the caller's own token.
reads.pyThe only module permitted to run a query.
executor.pyThe only module permitted to call a mutate.
api_version.pyThe API version pin, in one place and nowhere else.

06   Configuration reference

Three files. .env holds secrets and deployment facts; the two YAML files hold policy and are hot-reloaded without a restart.

.env

VariableWhat it does
GADS_WRITE_ENABLEDMaster kill switch. false makes the server read-only and hides every write tool. Default false — turning it on is deliberate.
GADS_REQUIRE_HUMAN_CONFIRMATIONRequire a person to approve each apply. Default true.
GADS_ENVproduction enforces https and a signing key; development relaxes both.
GADS_BASE_URLMust exactly match the origin registered in the Google OAuth client.
GADS_PORT8081. The read-only server already uses 8000.
GADS_OAUTH_CLIENT_ID / _SECRETThe Google OAuth client.
GADS_JWT_SIGNING_KEYStable random string. Without it, every restart logs everyone out. Required in production.
GADS_DEVELOPER_TOKENGoogle Ads API developer token, from the MCC.
GADS_LOGIN_CUSTOMER_IDYour manager (MCC) account, digits only.
GADS_TIER_CACHE_SECONDSHow long a resolved tier is reused. Default 60, max 900, 0 disables.
GADS_AUDIT_RETENTION_DAYSDays of audit files to keep. Default 400.

config/policy.yaml — the money rules

Hot-reloaded. A bad edit is refused and the last good version stays in force, with /healthz flipping to 503 so it does not pass silently.

  • allowed_customer_ids — the account allowlist. No wildcards. Nothing outside it can be read or written.
  • currency_code, timezone — the account's own, used for display and for which day the spend ceiling counts against.
  • limits.defaults and limits.tiers — min and max daily budget, max percentage increase, max CPC, and the per-user daily total. Tier blocks override defaults key by key.
  • rules — new entities start paused, block broad match under manual CPC, allowed final URL domains.
  • blocked_operations, plans.ttl_seconds.
Written in code, not trusted to config

The none and readonly tiers are pinned to zero in policy.py. Their blocks in the YAML are documentation. A config that simply omitted them would otherwise have them inherit the permissive defaults.

config/roles.yaml — who is what

mode: file reads the users: map — fine for staging. mode: google_ads resolves each person's tier from Google Ads itself, per account, which is the operational goal: add someone in the Ads UI and they work here with no developer involvement.

07   Deploying somewhere new

Ubuntu, Python 3.11+, Node for PM2, and a hostname you control. No Docker.

01

Google Cloud — OAuth client

Create an OAuth 2.0 Web application client. Add the authorised redirect URI, which must match GADS_BASE_URL exactly:

https://YOUR-HOST/auth/callback

Enable the Google Ads API on the project. On the consent screen, add the three scopes the server requests: openid, userinfo.email, and https://www.googleapis.com/auth/adwords.

Ask for adwords now

Adding a scope later forces every user to re-consent. The server requests all three from the start for that reason.

02

Google Ads — developer token and MCC

From your manager account, take the developer token (API Center) and the MCC customer ID, digits only, no dashes. A test-level token only works against test accounts — you need at least Basic access for real ones.

03

The machine

git clone <repo> /home/ubuntu/gads-write-mcp
cd /home/ubuntu/gads-write-mcp
python3 -m venv .venv
.venv/bin/pip install -e '.[dev]'
mkdir -p logs
.venv/bin/python -m pytest        # 392 pass, no network needed

The editable install is required — python -m gads_write.server will not resolve otherwise.

04

.env

cp .env.example .env
python3 -c "import secrets; print(secrets.token_urlsafe(64))"   # signing key

Fill in the OAuth client, the signing key, the developer token, the MCC ID, and your GADS_BASE_URL. Leave GADS_WRITE_ENABLED=false — you turn writes on last, deliberately, once everything else is verified.

05

Policy and roles

Edit config/policy.yaml: put your real customer IDs in allowed_customer_ids, set the currency and timezone to the account's own, and set limits you would genuinely be comfortable with someone hitting.

Set config/roles.yaml to mode: file with one lead to start. Flip to google_ads once a real non-admin user has been verified (see §09).

06

Nginx and TLS

sudo cp ops/nginx.conf /etc/nginx/sites-available/YOUR-HOST
sudo ln -s /etc/nginx/sites-available/YOUR-HOST /etc/nginx/sites-enabled/
sudo certbot --nginx -d YOUR-HOST
sudo nginx -t && sudo systemctl reload nginx

Change server_name and confirm proxy_pass matches GADS_PORT. Do not remove the buffering and timeout settings.

07

PM2

Set cwd in ops/ecosystem.config.js to the real deploy path, then:

pm2 start ops/ecosystem.config.js
pm2 save
pm2 startup          # survive reboot
instances must stay 1

Draft plans live in process memory. A second worker would not see a plan drafted by the first, and single-use enforcement — which is what stops a double-apply — would have a hole in it.

08

Verify, in order

curl -s localhost:8081/healthz       # {"status":"ok",...}
curl -s https://YOUR-HOST/healthz    # same, through Nginx + TLS
pm2 logs gads-write-mcp

Then connect from Claude as a custom connector pointed at https://YOUR-HOST/mcp, complete the Google login, and call health_check. It reports who the server thinks you are and what tier you hold.

09

Turning writes on

Only after everything above is verified. Set GADS_WRITE_ENABLED=true, pm2 restart gads-write-mcp, and pause one campaign that does not matter — on a test account first. Check the audit log has a line for it, then enable it again.

08   Moving it to another org

Nothing about this codebase is specific to one company except the configuration. There are no hardcoded customer IDs, limits, or emails in Python — a test fails the build if one appears. To repoint it:

ChangeWhere
HostnameGADS_BASE_URL, server_name in ops/nginx.conf, the OAuth redirect URI, DNS
Google identityNew OAuth client, new developer token, new MCC ID
Accounts and moneyallowed_customer_ids, currency_code, timezone, every limit in policy.yaml
Ad copy rulesrules.allowed_final_url_domains — the domains ads may point at
Peopleroles.yaml, or flip to google_ads mode and manage it in the Ads UI
Deploy pathcwd in ops/ecosystem.config.js
PortGADS_PORT and proxy_pass — only if 8081 is taken

Everything else — the gate, the tiers, the two-step write, the audit log — is domain-independent and needs no edits.

09   Before you turn writes on

Stated plainly, because a passing test suite is not the same as production-ready.

Open at the time of writing
  • The daily spend cap can be stepped over. It is read when the gate runs but not written until after the human approves. Confirm two plans before approving either and both pass the same check.
  • Shipped config is still placeholder. The allowlist is 0000000000, and roles.yaml ships mode: file, in which the tier resolver ignores the account — so the per-account model does not exist as configured.
Never exercised against a live account

Every test uses a fake executor or an offline client. Proto construction, enum lookups and update-mask logic are exercised for real, but no request has ever left the process. Before first live use: a real test-account ID in policy.yaml, then pause one campaign that does not matter.

One thing to verify on first deploy

Whether a non-admin can read their own access role from Google Ads. The whole "add them in the Ads UI and they just work" model rests on it. Have one real STANDARD or READ_ONLY user connect and call health_check. If it fails, the server says so loudly — an indeterminate lookup refuses rather than guessing — and roles.yaml in mode: file keeps the team working meanwhile.

Day-to-day commands

.venv/bin/python -m pytest              # no network, no credentials
curl -s localhost:8081/healthz          # 200 ok / 503 degraded
pm2 restart gads-write-mcp              # picks up .env and config/*.yaml
pm2 logs gads-write-mcp

Policy and roles hot-reload on save — a restart is only needed for .env changes.
