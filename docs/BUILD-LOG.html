What was built

An MCP server on adswrite.indiraivf.in, separate from the existing read-only server. Team members connect Claude with their own Google login; permissions come from Google Ads itself, so adding someone in the Google Ads interface is all that is needed to give them access here.

CapabilityDetail
ReadingAccounts, campaigns, ad groups, performance, search terms, and free-form queries for anything else
ChangingPause and enable campaigns, daily budgets, bids, keywords, negative keywords, new ads
ApprovalEvery change returns a preview first and applies only on a second, separate confirmation
PermissionsRead-only, operator and lead, resolved per account from each person's own Google Ads role
RecordEvery decision logged with who, when, what was approved and which resource changed — refusals included
SafetyAccounts limited to those under the manager account; no delete or remove operations exist; one switch makes the whole server read-only

Day by day

Dates and commit counts are taken from the repository history.

28 August Friday 1 commit
Set-up

Project established

Repository created as a separate service from the read-only Google Ads server already running, with its own process, hostname and deployment. Scope, constraints and the safety requirements written down before any code.

29 August Saturday 3 commits
Phases 1–2

Login, permissions and the gate

  • Google sign-in — every request authenticated with the user's own Google account; no shared or stored credential anywhere in the system
  • Permission tiers — read-only, operator and lead, with the rule that anything unrecognised gets no access rather than default access
  • The gate — a single checkpoint every request passes through, so a check cannot be forgotten on one operation and present on another
31 August Monday 9 commits
Phases 3–5

Reading, then the first write operations

  • Reading Google Ads — accounts, campaign performance and search term reports
  • Permissions from Google — a person's tier now derived from their actual Google Ads role rather than a list maintained by hand
  • Two-step changes — pause and enable built as draft-then-confirm, so nothing applies without a separate, deliberate second step
  • The full write set — budgets, bids, keywords, negative keywords and new ads

The heaviest day of the project. All money-handling written in millionths of a unit, the format Google requires, with a naming rule to make a missing conversion — a 1,000,000× error — visible in review rather than in an account.

1 September Tuesday 2 commits
Hardening

Closing a gap between drafting and applying

Found that the checks run when a change was drafted were stricter than those re-run when it was applied — meaning an approved change could take effect under rules it had never been tested against. Both steps now run identical code, with regression tests to keep them that way.

2 September Wednesday 6 commits
Phase 6

Operations, approval and monitoring

  • Human approval enforced by the server — the server itself stops and asks a person to accept the preview, rather than trusting the client to ask
  • Health endpoint — reports a fault to monitoring rather than running quietly on stale configuration
  • Self-managing audit log — rotates and prunes itself, so it needs no external maintenance
  • Two defects fixed — a malformed config crashing live requests, and a budget change that could check one budget and alter another
3 September Thursday 3 commits
Zero config

Removing the configuration file entirely

The server had a settings file listing permitted accounts, currencies and spending limits. It needed a developer for every change — which meant the marketing team could not manage their own tool.

  • Accounts now read from Google — linking a sub-account in the Google Ads interface is enough; nothing to edit here
  • Currency and timezone read per account — previously one setting for the whole server, which would have been wrong for any account not in rupees
  • Spending limits made proportional — rules that scale with the account instead of fixed amounts that go stale
Independent code review — 7 defects found

Five could have allowed a change that should have been refused. The most serious: a single typo in a settings value would have silently switched off the only remaining spending control while appearing to leave it on. All fixed, each with a test that reproduces the original fault.

4 September Friday 2 commits
Design change

Matching what the Google Ads interface already allows

Testing the rules against realistic scenarios showed several would have blocked ordinary work — raising a budget for a seasonal push, for instance, would have taken four days instead of one action. A tool people work around protects nothing.

Rules were reset around a clear principle: refuse only what cannot be undone, what falls outside our accounts, or what would make the preview misleading. Everything else is shown as a warning and left to the person approving — the same position they are in using Google Ads directly, but with a preview and an audit trail they do not get there.

5 September Saturday 2 commits
Live testing

First deployment and first real changes

  • Deployed and connected — sign-in, permissions and account listing all confirmed working against live Google Ads data
  • Read figures verified — reported spend cross-checked against Google's own totals to confirm the unit conversion was correct
  • First live change applied — a campaign paused end to end through preview, approval and audit
Defect found in live use

The very first attempted change failed. A parameter was being passed to Google in the wrong position — an error that would have blocked every write operation, and which the existing tests could not catch because the test stand-in accepted arguments the real Google client rejects. Fixed, and the stand-in now checks against the real interface so this class of fault fails during testing instead of in production.

7 September Monday 3 commits
Usability

Acting on what testing revealed

  • Tool grouping — read and write operations now declare themselves as such, so the connector can be set to ask before anything changes
  • Finding things — testing showed newly created campaigns were invisible to the server, because the existing reports only return items with recorded activity. Added the means to list campaigns and ad groups directly
  • General querying — rather than adding a tool per question, added one that answers any of them, so ads, assets, conversions and change history need no further development

Worth noting

  • No stored credentials. Every action uses the signed-in person's own Google account, so removing someone from Google Ads removes their access here immediately, with no change required to this system.
  • Nothing can be deleted. There are no remove operations at all. Pausing can be undone; deletion cannot, so it was left out deliberately.
  • Every action is recorded — including refused ones, which is how a limit set too tight for real work becomes visible rather than being quietly worked around.
  • Three rounds of review found real faults — an automated review, a live deployment, and hands-on testing each surfaced defects the previous stage had missed. The most serious two were found in the last week, both now covered by tests.
